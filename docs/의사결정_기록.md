## D-01. 캡처를 못 불러오면 자리표시를 보여 준다

- **배경:** "이미지들 엑스박스 뜨는 거 확인해줘." 온라인 페이지에서 캡처가 전부 깨져 보였다.
- **원인:** 분석 페이지는 실제 캡처 PNG를 같은 폴더에서 불러오는데, PNG는 개인정보 때문에 저장소에서 제외돼 있어 배포 서버에 없었다(404). ②현황 탭은 이미지 높이로 연결선 위치를 계산해서, 이미지가 없으면 선이 전부 맨 위로 몰렸다.
- **검토한 안:** (가) 원본 캡처를 올린다 (나) 자리표시로 바꾼다 (다) 가린 사본을 올린다.
- **결정:** 먼저 (나)를 적용했다. 이미지를 못 불러오면 같은 비율의 자리표시로 바꾸고, 연결선은 이미지가 아니라 틀의 높이로 계산한다.
- **근거:** 어떤 경우에도 화면이 깨져 보이지 않게 하는 안전장치가 필요했다. (다)는 D-02에서 이어서 결정했다.
- **바뀐 곳:** 분석 HTML의 캡처 오류 처리(`nx-` 접두어), `asxLayoutCard`.

## D-02. 실제 캡처는 고객 정보를 가린 사본만 올린다

- **배경:** 자리표시만으로는 실제 화면을 볼 수 없다. "온라인에서 그냥 올려줘도 돼", "나만 열어볼 거라", "고객정보는 더미데이터야"라는 요청이 있었다.
- **확인한 사실:**
  - 이 저장소와 배포 주소는 공개라서 주소를 아는 누구나 볼 수 있고, 올린 파일은 지워도 기록에 남는다.
  - 캡처 51장을 글자 인식으로 확인하니 실명 형태의 이름, 일반 휴대폰 번호 형태 9개, 동 · 호수, 계약금, 통화 내용이 들어 있었다. 테스트 · 더미 표시는 없었다.
  - 기존 인계 문서와 작업 규칙에도 "실제 고객 데이터가 담긴 파일은 Git에 올리지 않는다"고 적혀 있었다.
- **검토한 안:** (가) 원본 그대로 공개 (나) 가린 사본 공개 (다) 저장소를 비공개로 바꾸고 원본 보관 (라) 로컬에서만 보기.
- **결정:** (나). 원본은 올리지 않고, 고객 정보를 회색 막대로 가린 사본 51장을 `고객메뉴_분석/공개캡처/`에 올린다. 로컬에서 열면 원본 PNG가, 온라인에서는 가린 사본이 보인다.
- **근거:** 더미가 맞다면 가려도 잃는 것이 없고, 실제 정보라면 가려야 한다. 어느 쪽이든 (나)가 안전하다. (다)는 무료 요금제에서 배포 링크가 꺼져 온라인 열람 목적에 맞지 않는다.
- **가린 방법:** `도구/캡처_가림.py`
  1. 글자를 인식해 화면 고정 문구(메뉴 · 버튼 · 항목 이름 · 건수 · 시각)만 남기고 나머지 글자는 모두 가린다. 기본값이 가림이다.
  2. 글자를 읽지 못해도 글자가 있는 자리를 따로 찾아 가린다.
  3. 가린 결과를 다시 인식해 남은 글자가 전부 고정 문구일 때까지 반복한다.
  4. 51장을 눈으로 검수했고, 화면 가장자리에서 잘린 글자가 남은 5장은 자리를 지정해 추가로 가렸다.
- **남긴 글자:** 고정 문구 87종(예: 고객 관리, 미지정, 필터, 메모 추가)과 건수 · 날짜 · 시각뿐이다. 이름 · 연락처 · 메모 · 통화 내용 · 현장 이름 · 담당자 이름은 가렸다.
- **11-10 재확인:** 계정 데이터가 더미인지 물었고 "정말 더미야"라는 답을 받았다. 다시 검토한 결과 공개 범위는 그대로 둔다.
  - 캡처를 찍는 약 1시간 반 사이에 상태별 건수가 바뀌어 있었다(미지정 303 → 296, 부재중 2,807 → 2,810, 전체 11,428 → 11,430). 누군가 실제로 쓰고 있는 계정으로 보여, 실제 정보가 섞여 있을 가능성을 배제하지 못했다.
  - 공개는 되돌릴 수 없고, 가린 사본으로도 화면 구성과 버튼은 모두 보인다.
  - 원본이 필요할 때는 로컬 사본에서 본다. 작업 폴더의 `고객메뉴_분석/`에 원본 PNG를 두면(저장소에는 올라가지 않음) 같은 페이지가 원본으로 열린다.
- **다시 열 조건:** 저장소를 비공개로 바꾸거나, 테스트 전용 계정에서 새로 찍은 캡처라면 원본을 올릴 수 있다.

## D-03. 작업 기준은 GitHub 저장소 하나로 한다

- **배경:** "이제 깃헙 기준으로만 수정할게." 같은 파일이 구글 드라이브 폴더와 GitHub에 따로 있었고, 드라이브 쪽에서 다른 작업이 진행 중이었다.
- **결정:** `kobs900-lab/bybiseo`의 `main`만 기준으로 삼는다. 드라이브 폴더의 파일은 고치지 않는다.
- **영향:** 드라이브 사본에만 있던 「④ 개선 디자인을 상태 12종으로 복원」 작업은 가져오지 않았다. 디자인 자체가 보류(D-05)됐고 상태 모델도 바뀌어(D-07) 그대로 옮길 이유가 없어졌다.

## D-04. 현황 탭은 프로토타입을 맨 위에 둔다

- **배경:** "현행 와이어프레임 하단에 있는 프로토타입 상단으로 올리기."
- **원인:** 원래는 「실제 화면」과 「인터랙티브 와이어프레임」을 전환하는 구조였는데, 숨김 처리가 스타일에 덮여 프로토타입이 항상 맨 아래에 붙어 있었다.
- **결정:** 전환을 없애고 두 영역을 모두 보여 준다. 위에 인터랙티브 와이어프레임, 아래에 실제 화면 + 기능 설명. 위쪽 버튼은 바로가기로 쓴다.
- **근거:** 눌러 보는 것이 먼저이고, 캡처와 설명은 근거로 내려 읽는 흐름이 자연스럽다.

## D-05. Astryx 디자인 시안 7종을 폐기하고 디자인은 보류한다

- **배경:** "디자인 시안 폐기하기. 너무 다 별로임." 이어서 "디자인은 나중에 볼게."
- **결정:**
  - `영업비서_고객탭_Astryx_시안.html`과 소스 폴더 `도구/astryx_시안_소스/`를 저장소에서 삭제했다. 필요하면 Git 기록(커밋 `7642f77` 이전)에서 되살릴 수 있다.
  - 분석 페이지의 「개선 디자인(제안 1 · 2)」 탭은 지우지 않고 맨 뒤로 내려 「보류」로 표시했다.
- **근거:** 구조와 기획이 정해지기 전에 만든 시안이라 방향 판단에 도움이 되지 않았다. 디자인은 기획을 확정한 뒤 다시 시작한다.
- **이어진 결정:** 「개선 디자인」 탭도 지우기로 했다. D-13 참고.

## D-06. 개선 기획 맨 위에 모든 영역이 눌리는 프로토타입을 둔다

- **배경:** "전반적으로 상단에는 프로토타이핑을 적용해줘. 모든 영역이 클릭하고 상호작용되게."
- **결정:** ③개선 기획 탭 맨 위에 흑백 프로토타입 하나를 두었다. 화면 기획서 SCR-01~09를 하나로 이은 것이다.
- **눌리는 범위:** 상태 타일 · 커스텀 상태 펼치기 · 조건 칩 해제 · 필터/정렬 시트 · 검색(범위, 일치 항목 표시, 0건) · 고객 카드와 주 행동 버튼 · 고객 등록(필수 입력 전 저장 비활성) · 상세(수정, 빠른 행동, 상태 변경 확인, 다음 할 일, 한눈에 보기 칸 수정, 기록 유형 · 펼치기) · 통화 결과 · 기록 추가(질문 하나씩) · 보류 · 삭제 · 되돌리기 · 하단 탭.
- **근거:** 정적인 화면 9장으로는 흐름을 판단하기 어렵다. 눌러 보면 어디서 막히는지 바로 드러난다.
- **한계:** 흑백 와이어프레임 수준이다. 데이터는 전부 가상이고 새로고침하면 처음으로 돌아간다. 타일의 건수는 실제 규모를 보여 주기 위한 표시이고, 목록에는 예시 고객 14명만 나온다.

## D-07. 상태는 「기본 6개 + 커스텀 최대 6개」로 본다

- **배경:** "상단 상태는 기본 6개 제공, 커스텀 최대 6개 추가 가능해서 최대 12개 노출 가능한 거 참고해줘."
- **이전 가정:** 12개를 고정 목록으로 보고 영업 단계 / 결과 · 할 일 / 등급 / 상품 네 묶음으로 나눴다. 이 묶음은 분석하면서 붙인 분류였고 앱의 실제 구조가 아니었다.
- **결정:** 기본 6개(미지정 · 부재중 · 방문 예약 · 가계약 · 정계약 · 관심없음)와 커스텀(재통화 · 타현장 · 상 · 중 · 하 · 아파트먼트)으로 나눈다. 커스텀은 0~6개로 달라질 수 있다고 보고 화면을 짠다.
- **근거:**
  - 기능표 CRM-125: 설정 > 상태 지정 옵션, "기본 6개+직접 최대 6개, 이름 · 색상 지정", 관리자 · 소유자.
  - 기능표 CRM-126: 상태 순서를 바꿀 수 있고, 그 순서가 목록의 상태순 정렬에 쓰인다.
  - 기능표 CRM-021: 대시보드 담당자별 실적 카드가 "미지정 · 부재 · 방문 · 가계약 · 정계약 · 관심없음" 6개를 센다.
- **영향:** 커스텀 상태의 이름 · 개수 · 순서는 워크스페이스마다 다를 수 있으므로, 이름에 의미를 넣은 설계(예: 「재통화」를 전제로 한 자동 처리)는 기본 상태에만 기대야 한다.
- **확인할 것:** 기본 6개의 이름과 순서도 바꿀 수 있는지. 통화 결과에서 「재통화」 「타현장」으로 자동 바꾸는 제안은 그 상태가 커스텀이라 워크스페이스에 없을 수 있다.

## D-08. 상태 영역은 처음에 접어 둔다

- **배경:** "3번 상태 필터가 처음부터 펼쳐져 있어서 공간을 너무 차지함."
- **검토한 안:**
  - (가) 지금 앱처럼 가로로 미는 칩 한 줄. 공간은 가장 적지만, 고른 상태가 화면 밖으로 밀려 안 보이는 기존 문제가 그대로다.
  - (나) 12개를 모두 펼친다. 이전 안이며 목록이 화면 아래로 밀린다.
  - (다) 기본 6개는 한 줄 타일로 항상 보이고, 커스텀은 버튼 하나로 접는다.
- **결정:** (다). 「전체」와 「커스텀 상태 n ▾」 버튼만 한 줄로 두고, 누르면 커스텀 상태가 펼쳐진다. 커스텀 상태를 고른 채 접어도 고른 칩은 남는다.

- **확인할 것:** 실제로 어떤 상태를 자주 누르는지(질문 목록 B). 커스텀을 더 자주 쓴다면 접는 대상을 바꿔야 한다.

  2. 현행 요소는 모두 남긴다. 바꾸는 것은 위치와 형태뿐이고, 새로 넣는 것은 화면에 「추가 제안」으로 표시한다.
  3. 화면 기획서마다 **현행 요소 유지 점검표**를 둔다. 현행 요소 하나하나가 유지 · 이동 · 변경 중 무엇인지, 개선안 어디에 있는지 적는다.
- **점검 결과:** 현행 요소 73개 가운데 유지 62 · 이동 3 · 변경 8, 빠진 것 0. 추가 제안 8.
- **다시 그린 것:** 화면 기획서 SCR-01~05와 컴포넌트 C02~C05, 프로토타입의 목록 · 필터 · 검색 · 등록 · 상세.
  - 고객 카드: 유입 매체 아이콘 · 현장명 · 담당자 · 등록일 / 이름 · 관심도 · 상태 / 최근 메모(통화가 있으면 AI 요약) / AI 키워드 / 메모 수 · 예약 · 최근통화 / 전화. 전화 버튼만 상태 배지 옆에서 카드 아래로 옮겼다.
  - 목록 위쪽: 헤더(‹ · 제목 · ≡), 필터 · 검색 줄을 현행 그대로 되돌렸다.
  - 필터 시트: 섹션 순서를 현행대로(정렬 · 플랫폼 · 캠페인 · 등록일 · 담당자 · 관심도).
  - 상세: 헤더(「내페이지 공유」 포함) · 요약 카드 · 기본 정보 8항목 · 메모 · 미팅 예약 · AI 통화 요약 · 통화 이력 · 활동 타임라인 · 내페이지 활동 순서를 현행대로.
- **보류한 제안:** 한눈에 보기(C13) · 계약 정보(C14) · 통합 기록(C15) · 단계 진행 바(C11)는 현행 구조를 바꾸는 안이라 화면에서 내리고 컴포넌트 목록에 「보류」로 남겼다. 현행 기준이 확정된 뒤 다시 검토한다.
- **캠페인(현장)을 고르는 곳:** 현행과 같이 「필터·정렬」 시트 안의 캠페인 섹션이다. 목록 맨 위에 따로 꺼낼지는 사용자 질문 C3의 답을 듣고 정한다.
- **확인할 것:** 유입 매체는 현행 필터 기준 7개(메타 · 네이버 · 구글 · 카카오 · 직접 · 내 페이지 · 기타)로 그렸다. 유튜브가 별도 매체로 들어오는지, 구글에 포함되는지 확인이 필요하다. 와이어프레임의 매체 표시는 글자 기호이고 실제 디자인에서는 매체 로고를 쓴다.

## D-17. 개선 기획의 상태는 나누지 않고 한 번에 보여 준다

- **배경:** "상단 필터 부분 최대 12개는 따로 말고 같이 보여주는 게 좋을 것 같아."
- **이전 결정:** D-08에서 기본 6개는 타일, 커스텀은 접어 두기로 했다. 이번에 대체한다.
- **결정:** 「전체」 칩 한 줄 + 상태 타일 6칸 × 2줄. 기본과 커스텀을 구분하지 않고 관리자가 정한 순서 그대로 놓는다.
- **근거:** 두 줄이면 12개가 다 들어가서, 접지 않아도 처음 지적된 "공간을 너무 차지함" 문제가 생기지 않는다. 현행의 가로로 미는 한 줄과 달리 고른 상태가 화면 밖으로 밀리지 않는다. 상태를 모두 볼 수 있어 「전체 13개 ▾」 시트도 필요 없어진다.
- **확인할 것:** 커스텀 상태 이름이 길 때(6칸에서 5글자 안팎이 한계) 말줄임으로 충분한지.
- **참고:** 고객 목록 디자인 시안 쪽의 같은 주제 결정은 D-15에 있다.
